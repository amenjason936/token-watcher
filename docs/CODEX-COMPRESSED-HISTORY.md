# Codex 压缩历史与 7/30 天统计

## 漏计原因与修复范围

只扫描 `.jsonl` 会跳过仍保存在本机的 `.jsonl.zst` / `.jsonl.zstd` 历史。日期筛选和求和本身可以正确，但日志没有入库时，相应日期的总量仍会偏低。

采集器 v5 同时读取三种格式，压缩文件按完整快照处理；普通 JSONL 保留增量字节游标。普通、压缩和归档目录里的同名副本共用事件和工具调用去重键。文件解压失败时回滚当前文件的事务，健康检查显示解析错误。实现基于 [PR #2](https://github.com/luwill/token-watcher/pull/2)（horacehht，提交 `5e6f9f96fa5653a64f2a1bf77b837b6c4b74c87d`）。

这是磁盘文件压缩的读取修复，不改变 Codex 单次 token 用量和父会话历史重放的判断公式。恢复范围取决于本机仍存在的日志，无法找回已经删除的源文件。

## 时间窗口

| 位置 | 口径 |
| --- | --- |
| 本地面板、近 7 天卡片与费用、CSV、工具活动 | 操作系统本地时区，含今天的最近 N 个自然日 |
| 社区排行榜上报的用量与主力模型 | UTC，含今天的最近 7/30 个自然日 |
| 社区榜单 7/30 天排名 | 服务端实际收到的每日 UTC 用量之和 |

例如本地日期为 2026-10-10，7 天从 10-04 00:00 开始，30 天从 09-11 00:00 开始。北京/台北用户的本地日界相同，但其他时区用户按各自本地日期统计；不是统一写死北京时间，也不是滚动 168/720 小时。跨夏令时按日历移动起点。

若缺失日志全部位于 09-11 至 09-27，恢复后 30 天增加、7 天保持不变。若压缩文件也包含最近 7 天的请求，7 天同样需要补回；不能据一位用户的对账断定所有人的 7 天统计都不受影响。

## 更新与恢复

1. 使用包含采集器 v5 的版本。`token-watcher --version` 只显示已安装版本，不能把本地代码修复当作 npm 已发版。
2. 确认压缩日志可解码。Node 22.13 需要系统 `zstd` 命令；有内置 zstd 的 Node 可以处理本实现支持的单帧回落路径。多帧文件需要 `zstd` CLI。macOS 使用 Homebrew 时可执行 `brew install zstd`；其他系统使用对应包管理器安装。常驻服务会额外尝试常见的 zstd 绝对路径。
3. 备份当前用量数据库。更新正在运行的服务后，首次扫描会自动补读压缩日志并重扫 v4 游标；也可以在常驻扫描服务停止后手动运行 `token-watcher scan`。重扫会写入数据库，应由数据所有者确认执行，避免同时运行多个写库进程。
4. 检查 Codex 健康状态没有解析错误，并核对受影响日期及 7/30 天汇总。再次扫描不应重复计数。不要为补历史删除现有数据库或恢复过期备份。

## 云端不会自动补历史

当前社区 Worker 只接受当天 UTC 日期，用每天最后一次成功上报更新当天记录；7/30 天总量由这些日记录计算。客户端上传的周期总量用于一致性检查，不会直接替换排名总量。

因此 `token-watcher leaderboard push` 只刷新当天数据及周期模型，不能回填过去漏报的日期。本地恢复与云端历史修正是两项不同操作。若确需修正云端历史，应单独核验用户身份、UTC 逐日聚合和日期范围，备份后由管理员执行，并重新计算受影响窗口；本补丁不新增公开回填接口或放宽防伪造规则。

## 验证与反馈口径

`test/codex-zstd.mjs` 使用合成日志验证压缩读取、跨副本去重、重扫、版本升级、坏文件回滚和普通文件续写。`test/date-ranges.mjs` 验证日期边界、夏令时、卡片/图表/费用一致性、UTC 上报窗口，以及“7 天完整、30 天漏压缩历史”的恢复与复扫。

反馈截图中的 577 个文件、29,248 条记录、漏计约 33.56 亿 tokens 等是对方提供的私人数据对账结果，本仓库未包含其原始日志，不能把这些数字标为本项目独立复核通过。给反馈用户的准确说明是：压缩日志漏采已有代码修复；更新后可从仍保存在本机的日志重建相应日期；云端旧日期仍需单独处理。
